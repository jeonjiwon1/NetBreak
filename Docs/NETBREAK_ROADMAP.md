# NETBREAK 개발 로드맵 — Vertical Slice에서 상용 1.0까지

기준일: 2026-09-22. 이 문서는 개발 순서와 단계별 검증 목표를 정한다. 출시일, 데모 분량, 미확정 Area 2~6의 세부 게임 설계를 확정하지 않는다. 구현의 기준은 Git 저장소와 코드, 현재 상태의 기준은 [NETBREAK_STATE.md](../NETBREAK_STATE.md)다. 본 문서의 예정 항목을 구현 완료로 해석하지 않는다.

게임 설계 원칙은 [NETBREAK_DESIGN.md](NETBREAK_DESIGN.md), 성장 계약은 [NETBREAK_GROWTH_SYSTEM.md](NETBREAK_GROWTH_SYSTEM.md), 작업 규칙은 [AGENTS.md](../AGENTS.md)를 따른다.

## 전 단계 공통 원칙

- 모든 Run은 Area 1에서 시작한다. 해금된 마지막 해역까지 순서대로 진행하며 해역 이동은 새 Run 시작이 아니다.
- 같은 Run의 해역 사이에서는 Core/Partner, Tool Tree, E/R, 아이템, Gold, EXP, Level 등 성장 상태를 유지하고 설치물·활성 미끼·물고기·임시 오브젝트·인카운터 상태를 초기화한다. 새 Run에서는 Run 성장을 초기화한다.
- Meta 도구 해금과 현재 Run 소유를 분리한다. 정상 Area 1은 아이템을 지급하지 않는다.
- 한 Run의 고정 목표 플레이타임이나 절대 상한은 두지 않는다. 30분을 초과해도 그 자체로 문제가 아니고 1시간 이상도 허용하지만, 특정 시간을 채우려고 반복·대기·전투 수치를 억지로 늘리지 않는다.
- 구현된 해역 수를 기준으로 개별 해역 시간과 전체 Run 시간을 분리해 기록한다. 성장 밀도, 전투 변화, 전략적 판단과 지루함 여부를 플레이타임 길이보다 우선한다.
- 현재는 구조적 밸런스 문제만 우선 해결한다. 아이템별 최종 피해, 도구 DPS, 상점 가격·확률, 전체 경제·난이도·플레이타임의 정밀 조정은 콘텐츠가 충분히 연결된 뒤 수행한다.
- 외부 플레이테스트 전에 기본 조작 이해와 핵심 피드백을 확보한다. 반복되는 핵심 문제를 콘텐츠 양으로 덮지 않는다.
- Area 2는 콘텐츠 제작 파이프라인의 첫 실전 검증이다. Area 2~6 전체를 위한 거대한 선행 리팩터링은 하지 않고 실제 제작에서 확인된 반복 작업과 결합만 필요한 범위에서 데이터화한다.
- G6-C2까지 완료됐다. G7 이후 기능과 Area 2~6 콘텐츠는 예정 상태이며 완료로 기록하지 않는다.
- 새 콘텐츠는 가능한 한 gameplay, 아트·애니메이션, VFX, SFX, UI 아이콘·텍스트, 자동·수동 검증을 하나의 콘텐츠 단위로 묶는다. 모든 시각·청각 제작을 후반에 몰지 않되 최종 아트 폴리싱과 오디오 믹싱은 출시 준비에서 수행한다.
- 아트 표현 방식은 밝고 읽기 쉬운 탑다운 픽셀아트로 확정했다. 간결한 기본 스타일과 특수어·MiniBoss·Boss·주요 연출의 포인트 디테일 원칙을 사용한다. 정식 UI 폰트는 갈무리 9를 우선 후보로 검토한다. 세부 스프라이트 규격, 최종 팔레트, 정확한 에셋 수와 최종 VFX·사운드 에셋은 아직 미정이며 실제 아트·폰트 적용도 완료되지 않았다. 세부 기준은 [NETBREAK_ART_GUIDE.md](NETBREAK_ART_GUIDE.md)를 따른다.

## PHASE 1 — Area 1 Vertical Slice

**목표:** 이미 최소 안정화와 임시 전투 피드백이 검증된 G6-C2 기반 Area 1을 아트·사운드·온보딩까지 포함한 외부 테스트 가능 버티컬 슬라이스로 만든다.

현재 기준선은 대표 Area 1 성공 Run, MiniBoss/Boss 실패와 재시작, 새 Run 초기화, UX-F1과 UX-F2-A/B 임시 VFX 검증 완료다. 이는 정식 아트·VFX·오디오 완성을 뜻하지 않으며 상세 증거는 [NETBREAK_STATE.md](../NETBREAK_STATE.md)를 따른다.

### VS-1. 기존 전투 피드백 최소 점검 — UX-F3

- UX-F3의 범위는 **기존 E/R 및 MiniBoss/Boss 피드백 점검**이다.
- MiniBoss의 감속 후 돌진, Boss의 3회 회유와 관련 안내, 이미 구현된 E/R 기능과 연출을 실제 플레이에서 먼저 확인한다.
- 정보 전달 문제가 확인된 항목만 최소 수정한다. 문제가 없으면 새 기능이나 중복 연출을 추가하지 않고 종료한다.
- 정상 Area 1은 Boss 포획 보상으로 R을 얻은 직후 종료되어 후속 전투가 없다. R 전투 연출의 완성도는 Area 2 등 실제 후속 전투가 생겼을 때 다시 검증한다.
- UX-F3는 대규모 구현 과제나 이후 아트 제작의 필수 차단 단계가 아니다.

### VS-2. Area 1 아트 방향 확정

- [NETBREAK_ART_GUIDE.md](NETBREAK_ART_GUIDE.md)에 확정 방향, 화면 계층, 물고기·도구·배경·UI·VFX 원칙과 에셋 출처·라이선스 관리 기준을 기록한다.
- 현재 Camera, Sprite Importer, 기존 Sprite 크기·PPU와 UI Scaling을 조사할 계획을 세우고 실제 화면을 기준으로 제작 규격 후보를 정한다.
- 일반 물고기 1종, 오징어 1종, 낚싯대 1종, 바다 배경 1종과 기본 UI 아이콘 일부를 첫 스타일 프로토타입 범위로 둔다. 이는 Area 1 전체 확정 수량이 아니다.
- 갈무리 9의 공식 라이선스, 상업 이용·게임 패키지 포함·재배포 조건과 TMP 표시 품질을 확인한다. 현재 NanumGothic을 제거하거나 UI 폰트를 교체하지 않는다.
- 세부 Sprite 크기·PPU·Pixel Perfect Camera·내부 해상도·팔레트·애니메이션 프레임 수는 조사 전 확정하지 않는다.

### VS-3. Area 1 기본 아트 제작 및 적용

- 일반 물고기와 특수어, MiniBoss/Boss, 낚시 도구와 설치물, 바다·지형, 필수 UI·아이콘, 기본 애니메이션을 VS-2 규격에 따라 제작·적용한다.
- 실제 제작 범위와 에셋 개수는 아트 기획서에서 확정하며, 아직 정하지 않은 수량을 통과 조건으로 만들지 않는다.

### VS-4. 정식 핵심 VFX 적용

- 도구 사용·적중, 포획·다수 포획, 특수어 행동, 필요한 E/R·Boss 피드백, 아이템과 단일·복합 시너지를 정식 연출로 교체한다.
- UX-F1과 UX-F2-A/B의 실제 이벤트 연결 및 임시 VFX를 기반으로 삼되 정식 연출을 이유로 전투 판정이나 밸런스를 임의 변경하지 않는다.
- 정식 연출이 함께 발생할 때 효과 구분, HUD·성장 UI 가독성과 대규모 어군 성능을 다시 확인한다.

### VS-5. SFX 및 최소 BGM 적용

- 도구 사용·적중, 포획·보상, 스킬·특수어, Boss 경고·상태 전환에 필요한 SFX를 적용한다.
- 기본 조업 음악과 필요 시 Boss 음악을 마련한다. 정식 트랙 수는 사전 고정하지 않는다.
- 다수 물고기 동시 포획 등에서 SFX가 과다 중첩되지 않도록 재생 제한·우선순위 정책을 둔다.
- 음원 라이선스와 원본 출처를 기록하고 관리한다.

### VS-6. UX-F4 최소 튜토리얼

- 기존 Area 1 안에서 LURE → TRAP → CATCH, 핵심 조작과 포획 흐름, Core/Partner·Skill Tree·E/R, MiniBoss/Boss 규칙을 필요한 시점에 짧게 안내한다.
- 기존 모달 UI와 월드 입력이 충돌하지 않게 하고 건너뛰기와 다시 보기 필요성을 검토한다.
- 별도 튜토리얼 Scene 제작을 필수로 두지 않는다.

### VS-7. 버티컬 슬라이스 통합 검증

- Windows Build 생성·실행·재실행, 정상 성공/실패 Run과 새 Run 초기화를 확인한다.
- 주요 해상도, 다수 물고기 상황의 성능, 전투 연출과 UI 가독성, 오디오 믹싱·중첩을 점검한다.
- Console Error, 누락 참조, 입력 누수·모달 중첩과 진행 불가 결함을 확인한다.
- G10 관점에서 대표 Core/Partner 빌드 성립, MiniBoss/Boss 진행과 명백한 구조적 문제를 확인하되 최종 피해·경제·전체 Run 시간을 확정하지 않는다.

**다음 단계 판단:** 처음 보는 플레이어가 핵심 루프와 성장을 시험할 안내·시청각 피드백을 갖추고, 대표 성공·실패 경로와 배포 빌드에서 외부 테스트를 막는 결함이 없다.

## PHASE 2 — VS-8 소규모 외부 플레이테스트

**목표:** 대량 콘텐츠 확장 전에 실제 플레이어가 핵심 루프와 성장을 이해하고 즐기는지 확인한다.

- LURE → TRAP → CATCH가 이해되는지 관찰한다.
- Core/Partner 선택이 플레이에 차이를 만드는지 확인한다.
- 성장 선택이 재미있고 의미 있는지, 지루해지는 구간이 어디인지 기록한다.
- Boss 실패 이유를 이해하는지, 다시 플레이할 동기가 생기는지 확인한다.
- 포획·스킬·특수어·Boss의 시각 및 청각 피드백을 구분하고 이해하는지 확인한다.
- 플레이타임은 해역별/전체 Run으로 기록하지만 특정 시간 달성 여부로 평가하지 않는다.
- 반복적으로 발견되는 핵심 문제를 먼저 수정한다. 테스트를 막는 결함이 남아 있으면 대량 콘텐츠 제작으로 넘어가지 않는다.

**다음 단계 판단:** 핵심 조작과 성장의 이해도를 뒷받침하는 관찰 결과가 있고, 반복되는 주요 문제를 해결했거나 검증 가능한 개선 방향을 확보했다.

## PHASE 3 — 구조적 문제 수정과 G7/G8 성장·경제 연결

**목표:** 외부 테스트에서 반복 확인된 핵심 문제를 해결하고 미래 콘텐츠 확장에 필요한 성장·경제 계약을 작은 단위로 연결한다.

- 진행 불가, 입력·모달·참조 오류, 무한 피해·보상 중복·자원 증식, 선택 무력화처럼 확인된 구조적 문제를 우선 수정한다.
- 단순 취향이나 현재 제한된 콘텐츠만을 근거로 정밀 수치 조정을 반복하지 않는다.

- G7에서 상점과 Gold 소비 구조를 구현한다. 가격, 리롤, 확률, 등장 시점은 구현 전에 사용자와 별도로 확정한다.
- G8에서 해역별 보상 계약을 연결하고 기존 아이템 6종의 획득·강화 흐름을 재사용한다.
- 정상 Area 1 아이템 미지급 원칙을 임의로 바꾸지 않는다.
- Run 상태와 Meta 상태의 분리를 유지한다.
- 미래 전체 콘텐츠를 미리 구현하지 않고 Area 2 제작에 필요한 계약을 우선한다.

**다음 단계 판단:** 외부 테스트를 막은 구조적 결함이 해결되고 Area 2의 상점·Gold 사용·관문 보상을 실제 제작하며 검증할 수 있다.

## PHASE 4 — Area 2 제작 및 해역 전환 검증

**목표:** Area 2를 첫 실제 콘텐츠 확장으로 제작하며 지역 제작과 같은 Run 내 전환 구조를 검증한다.

- Area 1에서 Area 2로 정상 이동하고 기존 Run 성장 상태가 유지되는지 확인한다.
- 설치물·활성 미끼·물고기·임시 오브젝트·인카운터 상태가 초기화되는지 확인한다.
- 정상 아이템 보상을 연결한다.
- 새로운 경로·어종·MiniBoss·Boss 추가 방식을 실제로 검증한다.
- 현재 Main Scene을 재사용할지 지역별 Scene으로 분리할지 실제 제작 비용·참조·전환 요구를 기준으로 검토한다. 지금 전체 Scene 구조를 선행 대규모 리팩터링하지 않는다.
- 지역 전환, 결과, 실패와 재시작에서 Run 상태 유지와 해역별 월드 상태 정리가 섞이지 않는지 확인한다.
- 제작 과정에서 확인된 반복 작업과 강한 결합만 필요한 범위에서 데이터화한다.

**다음 단계 판단:** Area 2가 같은 Run에서 정상 연결되고, 다음 지역 콘텐츠를 주요 구조의 반복 재작성 없이 추가할 수 있는 제작 흐름을 확인했다.

## PHASE 5 — 도구·아이템·스킬·시너지 및 Area 3~6 콘텐츠 확장

**목표:** Area 2에서 검증한 파이프라인으로 콘텐츠를 작은 묶음부터 점진적으로 늘린다.

- 기존 전기/검/얼음 아이템을 확장할 수 있으며 새 효과·속성은 단계별로 검토한다.
- 새 도구는 기존 도구와 역할을 차별화하고 필요한 Tool Tree·시너지를 함께 검토한다.
- 새 콘텐츠마다 gameplay뿐 아니라 필요한 아트·애니메이션, VFX, SFX, UI 아이콘·한국어 텍스트와 자동·수동 검증을 같은 제작 단위로 계획한다.
- 첫 확장은 작은 묶음으로 제작하고 검증 결과에 따라 다음 규모를 결정한다. 아이템 3~6개 같은 수치는 제안일 뿐 확정 수량이 아니다.
- 추가 콘텐츠마다 기존 성장·보상·전투 회귀를 확인한다.
- 대표 빌드가 정상 Run에서 성립하는 시점부터 성장 속도, Gold 사용처, 빌드 다양성, 설치형 도구 의존도, 특수어·보스 대응과 시너지 효율을 중간 점검한다. 최종 수치는 확정하지 않는다.
- Area 3~6을 순차 제작하며 모든 Run이 Area 1에서 시작하고 해역을 순서대로 진행하는 규칙을 유지한다.
- G9 Legacy 정리는 관련 대체 시스템의 검증이 끝난 범위만 수행한다. 콘텐츠 제작을 막지 않는 휴면 코드의 대규모 정리를 우선하지 않는다.

**다음 단계 판단:** 전체 지역 제작이 진행되고 콘텐츠 추가가 기존 Run 흐름을 깨뜨리지 않으며, 전체 Meta와 정밀 밸런스에 필요한 대상이 충분히 구체화되어 있다.

## PHASE 6 — Full Meta Progression 및 Hard Mode

**목표:** 데모의 저장/진행 기반을 전체 게임의 영구 성장으로 완성한다.

- 지역·도구 해금, Meta Currency, 영구 성장과 Hard Mode를 완성한다.
- Run 상태와 Meta 상태를 분리하고 새 Run 초기화 및 같은 Run의 해역 이동을 함께 검증한다.
- 저장 데이터 버전 관리와 마이그레이션을 마련한다.

**다음 단계 판단:** 전체 게임의 해금·성장·저장 흐름이 연결되고 재실행과 버전 변경 뒤에도 진행 규칙을 유지한다.

## PHASE 7 — Alpha, 전체 Run 정밀 밸런스 및 최적화

**목표:** 1.0 핵심 시스템과 콘텐츠가 연결된 상태에서 전체 게임을 검증하고 정밀 밸런스를 시작한다.

- 시작부터 최종 결과까지 완전한 Run을 반복 테스트한다.
- 아이템별 피해, 도구 DPS, 상점 가격·리롤, 희귀도·등장 확률, 전체 경제와 해역 난이도 곡선을 조정한다.
- 전체 Run 플레이타임을 분석하되 고정 목표나 상한에 맞추지 않는다.
- 실제 병목을 기준으로 성능과 메모리를 최적화하고 대표 해상도·대규모 어군·장시간 Run을 회귀 검증한다.
- 진행 단절, 빠진 콘텐츠와 핵심 시스템 공백을 해결한다.

**다음 단계 판단:** 필수 1.0 범위가 실제로 연결되어 플레이 가능하고 안정화에 집중할 수 있다.

## PHASE 8 — Beta / Release Candidate

**목표:** 필수적인 경우를 제외하고 주요 신규 시스템을 추가하지 않으며 출시 안정성을 확보한다.

- 버그, 성능, 저장 안정성, UX와 접근성을 개선한다.
- 해상도·화면 옵션, 입력, 오디오 믹싱과 빌드 안정성을 검증한다.
- UI/UX와 그래픽·사운드를 출시 범위에 맞게 최종 폴리싱하고 오디오 믹싱과 수정 후 회귀 테스트를 완료한다.

**다음 단계 판단:** 출시 후보 빌드의 주요 결함과 저장·진행 위험이 해결되어 최종 배포 검증을 진행할 수 있다.

## PHASE 9 — Commercial 1.0 Release

**목표:** 상용 배포할 최종 빌드와 출시 자료를 준비한다.

- 실제 프로덕션 빌드를 만들고 해당 빌드로 최종 회귀 테스트한다.
- 스토어 이미지·소개·영상 등 출시 에셋과 체크리스트를 준비한다.
- 배포 빌드와 Git 버전을 식별할 수 있게 기록한다.

**완료 기준:** 1.0 빌드, 스토어 자료와 출시 체크리스트가 준비되어 최종 검증을 마친 버전이 배포됐다.

## PHASE 10 — Post-launch

**목표:** 실제 플레이 환경의 안정성을 우선하고 이후 투자를 플레이어 데이터로 판단한다.

- 충돌, 저장 손상, 진행 불가 등 치명적인 문제를 먼저 핫픽스한다.
- 실제 피드백과 플레이 데이터를 바탕으로 밸런스 업데이트와 추가 콘텐츠 필요를 평가한다.
- 업데이트마다 회귀 검증, 저장 호환성, Git 이력과 `NETBREAK_STATE.md` 갱신을 유지한다.

추가 콘텐츠 분량, 데모 범위, 출시 플랫폼 정책과 출시 일정은 별도 확정 전까지 미정이다.
